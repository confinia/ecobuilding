## 2. Which path is active in prod

The API reads BDNB from the **public api.bdnb.io** unless overridden:

- `BDNB_URL` / `BDNB_BASE_URL` (env, `api/app/main.py`) default to api.bdnb.io.
  Setting them to the local PostgREST (`http://host.containers.internal:3005/…`)
  cuts over to the self-hosted mirror with **config only, no code change**.
- `DVF_RPC_URL` (env) — **unset in prod today**, so building records carry no
  `prices` block. When set, the API calls the local `dvf.prices_for_building`
  RPC. A DVF failure never breaks a building record (logged, returns `None`).
- ⚠ The `BDNB_LOCAL=1` mentioned at the end of `deploy/bdnb-import.sh` is
  **stale** — no such switch exists; the cutover envs above are the real ones.

`docker-compose.yml` is the source of truth for this wiring (rule 2).

## 3. Live upstream calls: caching & quota guards

All upstream reads go through `_cached_get_json` (`api/app/main.py`):

- In-process **TTL + LRU** cache, max 5000 entries, hit/miss metric
  `ecobuilding_upstream_cache` (Grafana).
- TTLs: BAN search 1 h; BAN housenumber/reverse, BDNB by id, Géorisques,
  DVF RPC 24 h; Panoramax 1 h.
- Purpose: guard the **BDNB free tier (10k calls/month)** against spikes;
  building data changes rarely.
- The cache is per-process: it empties on restart/promote, and blue/green
  stacks each have their own.
- Additional guard: `ANON_DAILY_CAP` (default 20/day/IP) on the PDF fiche,
  with a friendly French 429 page.

## 4. Loading the BDNB mirror (self-hosting, [#28](https://github.com/confinia/ecobuilding/issues/28))

One-time (per millésime), **on the VM** as the `ecobuilding` user:

1. Download the BDNB open-data **pgdump** archive to `~/bdnb/bdnb_pgdump.tar.gz`
   (~40 GB; extracts to ~171 GB of SQL). **Never stage it in `/tmp`** — that is
   a 16 GB RAM tmpfs and will OOM the VM.
2. Run `./deploy/bdnb-import.sh`. It:
   - verifies the pinned SHA-256 (update the hash in the script for a new dump);
   - extracts and restores into the `bdnb-db` PostGIS
     (project `ecobuilding-bdnb`, volume `bdnb_pgdata`);
   - discovers the schema name (`bdnb_<millésime>_a_open_data`), creates the
     `bdnb_anon` read-only role, writes `PGRST_DB_SCHEMAS` to
     `deploy/secrets.env`;
   - starts PostgREST on `:3005`, which mirrors the api.bdnb.io query syntax
     (`?col=eq.val`) so the API only needs the base-URL swap (§2).
3. Restore takes hours; the DB runs with `fsync=off` (rebuildable mirror, never
   a source of truth) — a crash just means re-running the import.

⚠ `bdnb_stack/docker-compose.yml` sets `PGRST_DB_SCHEMAS: dvf` in
`environment`, which **overrides** the value the import writes to
`secrets.env` (compose precedence). Today PostgREST therefore exposes only the
`dvf` schema (the prices RPC). Full BDNB cutover requires exposing the BDNB
schema there too.

## 5. Loading DVF prices ([#89](https://github.com/confinia/ecobuilding/issues/89))

**On the VM**, after the BDNB restore (the join needs
`rel_batiment_groupe_parcelle`):

1. `nohup ./deploy/dvf-import.sh > ~/bdnb/dvf.log 2>&1 &` — streams the Etalab
   geo-DVF CSVs (years in `YEARS`, currently 2020–2025) straight into PostGIS
   (no disk staging), builds the typed `dvf.mutation` table (sales only),
   indexes on `id_parcelle` and `(code_commune, type_local)`, then validates
   the building↔parcelle join. Progress: `~/bdnb/dvf.status`.
2. Apply `deploy/dvf-prices-function.sql` — the `dvf.prices_for_building(id)`
   RPC (recent parcelle sales + commune median €/m², honest `available:false`
   for Alsace-Moselle/Mayotte which DVF does not cover).
   ⚠ The function **hard-codes the BDNB schema name**
   (`bdnb_2026_02_a_open_data`) — it must be edited and re-applied at each
   BDNB millésime change.
3. Wire `DVF_RPC_URL` on the API (§2).

## 6. Updating each dataset

| Dataset | Cadence | Procedure |
|---|---|---|
| BDNB mirror | CSTB publishes ~2 millésimes/year | New dump → update SHA-256 in `bdnb-import.sh` → re-run §4 (fresh volume is safest) → edit schema name in `dvf-prices-function.sql` and re-apply → re-run the DVF join validation |
| DVF | Etalab refreshes ~2×/year (spring/autumn) | Add the new year to `YEARS` if needed, re-run §5 — the import is a **full rebuild** (drops and recreates `dvf.mutation`; the RPC survives) |
| GeoIP | db-ip publishes monthly | Replace `data/geoip/dbip-country-lite.mmdb` on the VM manually — `deploy.sh` only copies it **if absent**, it never refreshes it |
| Live APIs (BAN, BDNB api, Géorisques, Panoramax, tiles) | Continuous upstream | Nothing to do — caches expire by TTL |
| Business data (`data/leads/`, Keycloak) | Runtime | Never "updated" in bulk; see backups §7 |

## 7. Backup / restore: precious vs re-fetchable

`deploy/backup.sh` (on the VM, cron-able) backs up **only the irreplaceable**:
Keycloak Postgres (accounts/orgs), `leads.jsonl`, Grafana DB — age-encrypted,
14 archives retained, off-site copy is the operator's job (SECURITY.md).

Open data (BDNB, DVF, BAN, Géorisques, GeoIP) is **never backed up**: it is
re-fetchable, and the mirror is rebuildable via §4–§5 (slow but safe).

`deploy/deploy.sh` rsyncs with `--delete` but **excludes `data/`** — runtime
data survives deploys; both blue/green stacks share `data/leads/` so no lead
is lost across promotes.

## 8. Gotchas

- **`/tmp` on the VM is a 16 GB RAM tmpfs** — never stage dumps there.
- **The VM's `curl` truncates large response bodies** — use Python/`httpx` to
  fetch PDFs/PNGs from the VM.
- rsync ships the **working tree** (gitignored files travel) — keep it clean
  before deploying.
- The BDNB DB runs with durability off (`fsync=off`) — expected for a mirror,
  fatal for anything precious: never store non-rebuildable data in it.
